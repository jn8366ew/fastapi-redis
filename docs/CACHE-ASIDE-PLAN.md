# Cache-Aside 효과 측정 실험 — 기획서

> Redis 캐싱 패턴이 실제로 DB 부하를 얼마나 줄이는지,
> 그리고 **언제 그 이득이 사라지는지**를 데이터로 검증하는 실험 프로젝트.

| | |
|---|---|
| 상태 | 기획 단계 (구현 전) |
| 대상 패턴 | Cache-Aside (Look-Aside) |
| 스택 | FastAPI · Redis · PostgreSQL · k6 · Docker Compose |

---

## 1. 문제 정의

학습용으로 Cache-Aside를 구현했으나, 현재 구조로는 **핵심 주장을 증명할 수 없다.**

```python
fake_db = {"user:1": {...}}      # 파이썬 dict
await asyncio.sleep(2)           # DB 지연 "흉내"
```

`dict` 조회는 **CPU도, 커넥션도, 디스크 I/O도 소비하지 않는다.**
`sleep(2)`는 그저 기다릴 뿐 어떤 자원도 쓰지 않는다.

따라서 지금 코드로 말할 수 있는 것은 여기까지다.

- ✅ "응답이 빨라졌다"
- ❌ "**DB 부하가 줄었다**"

두 번째 문장이 캐싱의 존재 이유인데, 그것을 측정할 수단이 없다.
이 간극을 메우는 것이 이 프로젝트의 출발점이다.

---

## 2. 실험 질문과 가설

### 실험 질문

> **캐시는 언제, 왜, 얼마나 이득인가 — 그리고 언제 그 이득이 사라지는가**

앞 절반은 누구나 다룬다. **뒷 절반이 이 프로젝트의 정체성**이다.
"캐시를 붙였더니 빨라졌다"는 결론이 뻔해서 변별력이 없다.
**이득이 사라지는 지점까지 측정**하면 벤치마크가 아니라 실험이 된다.

### 가설

결과를 보기 전에 가설을 명시해 둔다.
그래야 나중에 "예상대로" / "예상과 달리"를 말할 수 있고, 거기서 서사가 나온다.

| | 가설 |
|---|---|
| **H1** | 접근이 편향될수록(Zipf) 캐시 이득이 급증하고, **균등 분포에서는 거의 0에 수렴**한다 |
| **H2** | 캐시는 DB 포화점을 뒤로 밀지만, **평균이 아니라 p99에서 차이가 극적**이다 |
| **H3** | 쓰기 비율이 임계를 넘으면 무효화 비용이 이득을 잡아먹어 **캐시가 손해로 뒤집힌다** |
| **H4** | 현재 구조에서 Redis가 죽으면 DB가 멀쩡해도 **전체 장애**가 된다 |

H3와 H4가 검증되면 그것이 이 프로젝트의 하이라이트다.

## 3. 변수 설계

실험이 성립하려면 변수가 정리되어 있어야 한다.

### 독립변수 — 내가 흔드는 것

| 변수 | 수준 |
|---|---|
| 접근 분포 | 균등 / Zipf(80:20) / 단일 핫키 |
| 동시성 | 10 → 50 → 100 → 200 VU |
| TTL | 10s / 60s / 300s |
| 쓰기 비율 | 0% / 10% / 30% |
| 캐시 생존 | 정상 / Redis 강제 종료 |

### 종속변수 — 측정하는 것

| 층위 | 지표 | 수집 방법 |
|---|---|---|
| 사용자 체감 | p50 / p95 / **p99** / RPS / 에러율 | k6 summary JSON |
| **DB 부하** ← 핵심 | 쿼리 수 / 활성 커넥션 / 버퍼 히트율 | `pg_stat_statements`, `pg_stat_database` |
| 캐시 | Hit rate / 메모리 / 키 수 / eviction | Redis `INFO` |
| 컨테이너 | CPU / 메모리 | `docker stats` 주기 샘플링 |

**평균이 아니라 p99와 DB CPU가 결론의 주인공이다.**
평균은 캐시 히트에 희석되어 실제 사용자 경험을 가린다.

### 통제변수 — 고정해야 하는 것

- 데이터 양, 쿼리 형태, 하드웨어
- 커넥션 풀 크기, 워밍업 시간, 측정 구간 길이

> 통제변수를 명시하는 것이 아마추어 벤치마크와 갈리는 지점이다.

## 4. 대조군 설계

같은 애플리케이션 안에 두 경로를 두고, **캐시 유무만 다르게** 한다.

```
GET  /v1/products/{id}           대조군 — DB 직행
GET  /v2/products/{id}           실험군 — Cache-Aside

POST /v1/products/{id}/reviews   쓰기 (무효화 없음)
POST /v2/products/{id}/reviews   쓰기 + 캐시 무효화
```

별개 애플리케이션으로 나누면 "다른 조건 때문 아니냐"는 반박이 가능해진다.
**같은 프로세스 · 같은 커넥션 풀 · 같은 쿼리**를 공유해야
차이의 원인이 캐시 하나로 좁혀진다.

## 5. 데이터 전략

### 합성 데이터를 쓰는 이유

공공 데이터셋 대신 `generate_series`로 DB 안에서 직접 생성한다.

| 이유 | 설명 |
|---|---|
| **재현성** | `docker compose up` 하나로 누구나 동일 데이터. 수동 다운로드 단계가 없음 |
| **크기가 다이얼** | 행 수를 실험 축으로 사용 가능. 고정 데이터로는 불가능 |
| **분포 통제** | 핵심 축이 "접근 편향"인데, 데이터 자체 편향도 통제해야 변수 통제 성립 |
| **속도** | SQL 생성은 500만 행 1분 이내. 파이썬 Faker는 30분 |

### 도메인 — 이커머스 상품 상세

단순 `users` 조회보다 이 도메인이 나은 이유:

1. 캐싱을 **실제로 가장 많이 쓰는 워크로드**
2. 집계(평균 평점, 리뷰 수)가 **자연스럽게 무겁다** — 억지 `sleep` 불필요
3. **리뷰 작성이라는 쓰기 이벤트**가 무효화 시나리오와 그대로 맞물린다

### 스키마

```
sellers      1만 건
products    50만 건    ← 캐시 키 50만 개 (Zipf 실험에 충분한 카디널리티)
reviews    500만 건    ← 집계 대상, 상품당 평균 10건
```

- 행 수는 환경변수로 파라미터화 (`SEED_PRODUCTS`, `SEED_REVIEWS`)
  → 빠른 반복용 **SMALL 모드**, 본 실험용 **FULL 모드**
- 리뷰를 인기 상품에 의도적으로 편중시켜 현실 반영

### 측정 대상 쿼리

```sql
SELECT p.*,
       s.name, s.rating,
       AVG(r.rating) AS avg_rating,
       COUNT(r.id)   AS review_count
FROM products p
JOIN sellers s      ON s.id = p.seller_id
LEFT JOIN reviews r ON r.product_id = p.id
WHERE p.id = $1
GROUP BY p.id, s.id;
```

## 6. 실험 설계의 핵심 기준

여기가 이 기획의 성패를 가른다.

> ### 캐시 미적용 p95가 **50~200ms** 나오도록 데이터와 쿼리를 맞춘다

행 수를 먼저 정하는 것이 아니라 **응답시간 목표에서 역산**한다.

| 상황 | 문제 | 대응 |
|---|---|---|
| p95 < 10ms | DB가 이미 빨라서 캐시 효과가 안 보임 | 리뷰 수 증가 / 조인 추가 / 인덱스 제거 |
| p95 > 500ms | 실험 한 번에 하세월 | 인덱스 추가 |
| **50~200ms** | ✅ 캐시 적용 시 1~3ms → **50~100배 개선이 그래프에 선명** | — |

### 왜 데이터가 충분히 커야 하나

한 행을 200바이트로 잡으면 1만 건은 **2MB**다.
PostgreSQL 기본 `shared_buffers`가 128MB이므로 **테이블 전체가 메모리에 상주**한다.
이러면 DB 조회가 이미 1ms 미만이라, 캐시를 붙여도 *1ms → 0.5ms* 라는
볼 것 없는 결과가 나온다.

```
캐시 이득  ∝  데이터 양  ×  쿼리 복잡도
```

500만 건이어도 **PK 단건 조회**면 1ms에 끝나 소용없다.
20만 건이어도 **조인 + 집계 + 정렬**이면 200ms가 나온다.

### 검증 방법

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT ... ;
```

`read=` 값(디스크에서 읽은 블록)이 **0이 아니어야** 한다.
0이면 전부 메모리 히트 = 실험 무의미.

## 7. 실험 매트릭스

각 축을 하나씩 흔들어 **곡선**을 뽑는다. 단발 벤치마크가 아니라는 것이 핵심.

| # | 흔드는 축 | 보고 싶은 것 |
|---|---|---|
| **A** | 접근 분포<br>균등 → Zipf(80:20) → 단일 핫키 | 히트율에 따른 이득 곡선.<br>**균등 분포에서는 캐시가 거의 무용**이라는 반직관적 결과 |
| **B** | 동시성<br>10 → 50 → 100 → 200 VU | DB가 무릎 꿇는 **포화점**이 캐시로 얼마나 밀리는가 |
| **C** | TTL<br>10s / 60s / 300s | 히트율 ↔ 데이터 신선도 트레이드오프 |
| **D** | 쓰기 비율<br>0% / 10% / 30% | **무효화가 잦아지면 캐시가 손해로 뒤집히는 지점** |
| **E** | Redis 강제 종료 | 캐시 장애 = 전체 장애임을 실증 (fail-open 부재) |

**D와 E가 차별 포인트다.** "캐시를 쓰면 안 되는 경우"를 데이터로 제시하는
지원자는 드물다.

### 부수적으로 관찰될 현상

| 현상 | 언제 나타나나 |
|---|---|
| **Cache Penetration**<br>(캐시 관통) | 존재하지 않는 ID 반복 조회 시. 404는 캐싱되지 않으므로 매번 DB 도달 → 공격 벡터 |
| **Cache Stampede**<br>(캐시 스탬피드) | TTL 만료 직후 동시 요청이 전부 Miss → DB 폭주. 캐시가 있으나 마나가 되는 순간 |

관찰되면 기록한다. 다음 단계(패턴 확장)의 동기가 된다.

## 8. 현업 아키텍처 대조

### 실무의 전체 구조

```
                        [ Client ]
                             |
                    +--------v--------+
                    |      CDN        |  <- (0) 엣지 캐시
                    |  CloudFront     |     수 분~수 시간 TTL
                    +--------+--------+
                             |
                    +--------v--------+
                    |  L7 LB / API GW |  ALB, Nginx, Kong
                    +--------+--------+
             +---------------+---------------+
             |               |               |
        +----v----+     +----v----+     +----v----+
        | API #1  |     | API #2  |     | API #3  |   stateless, N대
        |+-------+|     |+-------+|     |+-------+|
        || L1    ||     || L1    ||     || L1    ||  <- (1) 로컬 인메모리
        || Local ||     || Local ||     || Local ||     Caffeine / LRU
        |+-------+|     |+-------+|     |+-------+|     TTL 1~10초
        +----+----+     +----+----+     +----+----+
             |               |               |
             +---------------+---------------+
                             |  (2) L2 조회 (~0.5ms)
                  +----------v----------+
                  |    Redis Cluster    |  ElastiCache / MemoryDB
                  |  +------+  +------+ |
                  |  |Prim. |--|Repl. | |  <- 자동 페일오버
                  |  +------+  +------+ |
                  +----------+----------+
                             |  (3) Miss 시에만
                  +----------v----------+
                  |     RDS / Aurora    |
                  |  Writer ---> Reader |  <- (4) 읽기는 레플리카로
                  +---------------------+
```

### 이 프로젝트의 위치

> 우리가 만드는 것은 위 그림의 **(2) Redis ↔ (3) DB 구간 하나**다.
> 실무는 그 위아래로 캐시가 더 겹쳐 있다.

**핵심 인식: 캐시는 한 겹이 아니다.**

```
브라우저  →  CDN  →  앱 로컬(L1)  →  Redis(L2)  →  DB 버퍼풀
```

각 층이 히트율 50%씩만 걷어내도, 맨 아래 DB에 도달하는 요청은 극소수가 된다.

### 실습에 없는 현업 요소 5가지

#### ① L1 로컬 캐시 — Redis 앞의 캐시

Redis 왕복도 0.5ms이고 네트워크·커넥션을 소비한다. 초당 수만 요청이면
이조차 부담이라, 앱 프로세스 메모리에 **1~10초짜리 초단기 캐시**를 하나 더 둔다.

문제는 서버마다 값이 달라진다는 것. 그래서 TTL을 아주 짧게 가져가거나
④번 방식으로 무효화를 전파한다.

#### ② Fail-Open + Circuit Breaker

**실험 E에 대한 현업의 답이다.**

```
Redis 조회 실패
   → 예외를 삼키고 DB로 우회
   → 로그·메트릭만 남김
   → 서비스는 "느려질 뿐" 계속 동작
```

여기에 Circuit Breaker를 붙여, Redis가 연속 실패하면 **일정 시간 시도조차 하지 않는다.**
죽은 Redis에 매번 타임아웃(수백ms)을 기다리면
캐시가 오히려 서비스를 **더 느리게** 만들기 때문이다.

#### ③ Stampede 방어

| 방법 | 설명 |
|---|---|
| 분산 락 / single-flight | 첫 요청만 DB에 가고, 나머지는 대기 후 결과 공유 |
| TTL 지터 | `300초` 대신 `300±30초` 랜덤. 만료 시점을 흩뜨림 |
| Refresh-Ahead | 만료 전에 백그라운드로 미리 갱신 |

#### ④ 무효화 전파 (Pub/Sub · CDC)

앱 서버가 10대면 L1 캐시도 10개다. 한 대에서 데이터가 바뀌면 나머지 9대에 알려야 한다.

```
DB 변경  →  Redis Pub/Sub 브로드캐스트  →  전 서버 L1 무효화
```

더 큰 규모에서는 **DB 변경 로그를 직접 구독**한다
(Debezium → Kafka → 무효화 컨슈머).
애플리케이션 코드가 무효화를 빠뜨려도 DB 변경은 놓치지 않는다는 것이 장점.

#### ⑤ 관측

**Hit rate가 가장 중요한 지표다.** 이것이 떨어지면 곧 DB가 죽는다.

- Hit rate / Redis 메모리 / **eviction 수** / 키 개수
- eviction 급증 = 메모리 부족으로 캐시가 쫓겨나는 중 → 증설 신호
- p99 레이턴시와 DB 활성 커넥션 수를 나란히 모니터링

### 실험 → 현업 해법 매핑

이 프로젝트의 가장 중요한 표.
**실습에서 발견할 문제가 곧 위 항목들의 존재 이유다.**

| 실험에서 관찰 | 현업의 대응 |
|---|---|
| **E**: Redis 죽으니 전체 장애 | ② Fail-Open + Circuit Breaker |
| **B**: TTL 만료 직후 DB 폭주 | ③ 분산 락 · TTL 지터 |
| **D**: 쓰기 늘자 캐시가 손해 | Write-Through / Write-Behind |
| **A**: 균등 분포엔 캐시 무용 | 캐싱 대상 선별 (전부 캐싱하지 않는다) |
| Redis 왕복조차 부담 | ① L1 로컬 캐시 |

> **"문제를 직접 재현 → 현업 해법으로 연결"**
> 남의 글을 정리한 것이 아니라 직접 부딪혀 알게 됐다는 증거가 된다.

## 9. 예상 스토리라인

최종 README가 이렇게 흐르면 성공이다.

```
1. 캐시를 붙였다 → p99가 180ms에서 3ms로            (예상된 결과)
2. 그런데 균등 분포에서는 개선이 거의 없었다          (첫 반전)
3. 쓰기가 30%를 넘자 캐시가 오히려 느려졌다           (핵심 발견)
4. Redis를 껐더니 DB는 멀쩡한데 서비스가 죽었다        (설계 결함 발견)
5. → 그래서 다음 패턴이 필요하다                      (확장으로 연결)
```

**2 · 3 · 4번이 이 프로젝트를 남들과 구분 짓는다.**
실패와 한계를 데이터로 제시하는 것이 신뢰를 만든다.

## 10. 알려진 한계

부하 생성기(k6)와 측정 대상(API + DB)이 **같은 호스트**에서 실행된다.
고부하 구간에서 서로 CPU를 경쟁하므로, "DB가 느려진 것인지 k6가 느려진 것인지"
구분이 어려워진다.

따라서:

- 동시성은 **200 VU 선에서 멈춘다** (그 이상은 k6 자체가 병목일 수 있음)
- **절대 수치가 아닌 상대 비교로만** 결론을 낸다

> 한계를 숨기지 않고 명시하는 것이 오히려 실험 설계를 이해한다는 신호가 된다.

## 11. 확장 — 캐싱 패턴 시리즈

전략을 교체 가능한 구조로 뼈대를 잡아두면,
다른 패턴을 **같은 측정 하네스에 그대로 꽂을 수** 있다.
벤치마크 코드는 재사용하고 전략만 갈아끼운다.

```
app/strategies/
├── base.py          # 공통 인터페이스
├── nocache.py       # 대조군
├── cache_aside.py   # ← 현재
├── read_through.py
├── write_through.py
├── write_behind.py
└── refresh_ahead.py
```

9장의 반전들이 자연스럽게 다음 패턴의 **동기**가 된다.

> "쓰기가 많으면 Cache-Aside가 불리하다 → 그래서 Write-Through를 본다"

각 패턴마다 동일한 실험 A~E를 돌려 비교하면 시리즈로 이어지는 구조가 된다.

## 12. 구현 계획

### 확정된 결정

| 항목 | 선택 | 근거 |
|---|---|---|
| DB | PostgreSQL 17 (Docker) | dict로는 DB 리소스 절감 측정 불가 |
| 데이터 | 합성 (`generate_series`) | 재현성 · 크기 조절 · 분포 통제 |
| 도메인 | 이커머스 상품 상세 | 집계가 무겁고, 쓰기가 무효화와 맞물림 |
| 부하 도구 | k6 (`grafana/k6` 이미지) | 호스트 설치 불필요, 부하기가 병목 안 됨 |
| 관측 | 경량 자체계측 → 추후 Grafana | 인프라 삽질로 학습이 막히는 것 방지 |

### 파일 구조

```
fastapi-redis/
├── docker-compose.yml        # postgres, redis, api
├── db/
│   ├── schema.sql            # 테이블 + 인덱스
│   └── seed.sql              # generate_series 벌크 생성
├── app/
│   ├── main.py               # 엔드포인트 등록
│   ├── db.py                 # asyncpg 커넥션 풀 (lifespan)
│   ├── cache.py              # Redis 풀 (lifespan)
│   └── strategies/           # 패턴 확장 지점
├── bench/
│   ├── scenarios.js          # k6 시나리오
│   └── results/              # CSV/JSON 결과 (git 커밋)
├── analyze.py                # 결과 → 그래프
└── docs/PLAN.md              # 이 문서
```

**결과 파일을 git에 커밋하는 것이 중요하다.**
그래프를 언제든 재생성할 수 있다는 것이 신뢰의 근거가 된다.

### 기존 코드에서 이식할 것

현재 `main.py`에서 검증된 패턴은 그대로 가져간다.

- `lifespan`으로 커넥션 풀 생성/해제
- `app.state`에 풀 보관 → `request.app.state`로 접근
- `decode_responses=True` (없으면 `json.loads`가 bytes에서 실패)
- `json.dumps` 직렬화 + `set(..., ex=300)` TTL
- **무효화 순서: DB 먼저 → 캐시 삭제** (반대면 옛 값이 다시 캐싱됨)
- **갱신이 아닌 삭제로 무효화** (동시 쓰기 시 순서 역전 방지)

### 진행 순서

| 단계 | 내용 |
|---|---|
| 1 | **환경** — compose(postgres+redis+api), schema.sql, seed.sql |
| 2 | **쿼리 튜닝** — `EXPLAIN (ANALYZE, BUFFERS)`로 p95 50~200ms 맞추기 |
| 3 | **엔드포인트** — strategies 구조로 v1/v2 구현 |
| 4 | **부하 스크립트** — k6 시나리오, 분포 함수(균등/Zipf) |
| 5 | **실험 A~E 실행** — 결과를 `bench/results/`에 커밋 |
| 6 | **분석·문서화** — `analyze.py`로 그래프, README 작성 |

> **2단계에서 반드시 한 번 멈추고 수치를 확인한다.**
> 쿼리가 충분히 무겁지 않으면 이후 실험이 전부 무의미해진다.

### 검증 계획

- **환경** — `docker compose up` → `/docs` 접속, `/v1`·`/v2` 모두 200 응답
- **데이터** — `SELECT count(*)` 로 시드 확인, `EXPLAIN`에서 `read=` > 0
- **캐시 동작** — 같은 상품 2회 조회 시 2번째가 Hit.
  리뷰 POST 후 재조회 시 Miss 발생 (무효화 성공)
- **실험** — `docker compose run k6 run bench/scenarios.js` → 결과 JSON 생성
- **최종** — `uv run python analyze.py` → 그래프가 README 수치와 일치
